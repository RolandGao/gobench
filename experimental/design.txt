Experimental LLM Interface — High-Level Design
=============================================

Status: initial implementation in experimental/llm.py, authorized by the user.
Offline contract tests live in experimental/test_llm.py. Live-provider tests are
opt-in; passing the offline suite does not establish account/model availability.

1. Purpose and scope
--------------------

Provide one resumable, task-independent interface for direct model calls:

    response = player.input(prompt)

Support single-turn calls and multi-turn conversations, with explicit OAuth or
API-key authentication. The caller should not need to construct provider
requests, retain conversation history, or refresh authentication.

Applications own prompts, response interpretation, orchestration, and scoring.
Go rules, move parsing, opponents, matchmaking, and game recovery remain outside
this interface. GoBench records session directories in its own durable state
and reopens those LLM sessions when resuming.

All new work lives under experimental/. Keep arena.py and its existing workflow
unchanged. The implementation belongs in experimental/llm.py and its tests in
experimental/test_llm.py. Multiple internal classes may live in that one
implementation file. Avoid importing arena.py as the runtime foundation.

2. Public interface
-------------------

Current API:

    with LLM(
        name=model_name,
        mode="multi_turn",
        reasoning_effort="high",
        auth="oauth",
        session_dir="./sessions/player-1",
    ) as player:
        response = player.input(prompt)
        print(response.text)

Do not expose a required provider parameter. Infer the provider from a maintained
model-name registry and explicit aliases. Reject unknown or ambiguous names;
do not guess a provider or silently substitute another model. Save the resolved
provider and model identity so reopening does not reinterpret a changed alias.

The only modes are:

* single_turn: every input uses fresh model context. Prior calls remain in the
  durable journal but are not sent as conversation.
* multi_turn: inputs retain the session's conversation, including native reasoning
  items and signatures where returned and supported for replay.

No model tools are enabled in either mode. Initialization validates the complete
combination of model, mode, reasoning effort, and authentication. Reasoning
settings must map to supported native controls; do not silently drop unsupported
settings. Record the resolved request configuration.

Return a structured response with text, turn ID, provider response identity where
available, usage, timing, and completion status. Preserve provider-native request
and response bodies needed for audits and recovery, excluding credentials.
Missing usage remains unknown rather than being reported as zero. Distinguish
request elapsed time from provider-reported inference timing when available.
Preserve finish reasons, including refusals and output limits, so receiving a
response does not imply the requested task was completed successfully.

Ordinary interaction stays as simple as input(prompt). Additional operations
support turn lookup, cancellation, closing, and reopening a session.

The initial registry supports OpenAI (gpt-5.4, gpt-5.5, gpt-5.6-sol,
gpt-5.6-luna, gpt-6-astra) and Anthropic (claude-opus-5, claude-fable-5-1),
with the explicit aliases in MODEL_REGISTRY. Other names fail validation.
Both providers have API-key and direct OAuth transports. The implementation
uses provider request formats and subscription-login conventions already used
in this repository; it does not launch an agent runtime.

New sessions require name and auth; mode defaults to single_turn. Omitted
reasoning_effort uses the provider default. timeout defaults to 300 seconds for
the whole input, including authentication and retries. max_attempts defaults to
2, limited to known safe failures. API output limits default to 8192 tokens.
OpenAI OAuth uses its endpoint's output default and rejects an explicit
max_output_tokens rather than silently dropping it.

get_turn(id) returns a Turn record containing state, response, error, and native
attempt records. list_turns() and events() expose durable history for inspection.
reset(reason=...) explicitly starts fresh context without removing prior turns.

3. Authentication
-----------------

Authentication is explicit: auth="oauth" or auth="api_key". Do not silently fall
back from one to the other. Each provider adapter declares the authentication
methods supported for its models and endpoints; unsupported combinations fail
clearly. Do not assume OAuth is available for every provider or model.

Resolve credentials separately from session data. Persist the selected auth
method and any non-secret credential-profile reference, never API keys, access
or refresh tokens, or authorization headers in the session journal. Renewed
credentials can be used when reopening the same session.

The OAuth adapter handles token expiry and refresh through its credential store.
Coordinate concurrent refreshes that use the same credentials. If login or
reauthorization is required, return an explicit authentication error rather than
changing auth methods. API keys are obtained from the configured credential
source. Authentication failures and renewal follow the same request-retry rules
as other failures; refreshing credentials must not silently duplicate a turn.

API-key sources default to OPENAI_API_KEY and ANTHROPIC_API_KEY; api_key_env
selects another environment variable. OAuth uses credential_file or the
OPENAI_OAUTH_FILE / ANTHROPIC_OAUTH_FILE environment variables, otherwise the
provider's existing local login file. Saved sessions retain the resolved source
reference, and refreshed credentials are reread for subsequent requests. Initial
interactive login is external to this library. A durable refresh guard prevents
replaying a possibly consumed refresh token after a crash or lost token response.

4. Durable sessions
-------------------

Require session_dir for both modes. A new directory creates a session; an
existing valid directory resumes it. Permit reopening from session_dir alone,
using saved configuration. Any explicitly supplied conflicting configuration
fails initialization. Never overwrite an unrecognized directory. Recognized
interrupted initialization must be completed or rolled back safely before use.

Persist at least:

* Schema version, stable session ID, and resolved provider/model/mode/auth/effort.
* Conversation policy, including context-overflow/reset behavior.
* A journal of inputs, completed responses, failures, request attempts, and usage.
* Provider-native conversation data and recoverable request/response identifiers.

Do not silently truncate, summarize, or reset multi-turn history on context
overflow. Default to an explicit context-limit error. Any supported reset must
be explicitly requested and recorded while preserving prior journal entries.

Write durable state atomically where appropriate and serialize access to each
session. Concurrent processes must not independently advance the same session.
Persist completed responses before returning them. Never infer retry identity
from prompt text: identical prompts can represent different turns.

The implementation uses session.sqlite3 with fully synchronous transactions for
turns, native request/response records, conversation state, and audit events.
An exclusive process lock is held for the session's lifetime. Initialization
publishes a recognizable marker before creating the database, so an interrupted
creation can be completed safely. Credentials remain outside this database.

Resumption restores committed conversation and request records. It does not
restore process memory or open network connections. Provider adapters must retain
enough native state for replay or explicitly report that continuation cannot be
recovered; they must not silently start a fresh conversation.

5. Turn recovery and cancellation
---------------------------------

Turn identity and commit:

* Support input(prompt, turn_id=...) and get_turn(turn_id). Names are provisional.
  The caller saves its chosen ID before calling input when it needs recovery
  across its own crashes. Otherwise the interface generates an ID and exposes
  it in the response and journal; lookup operations expose unfinished turns.
* An ID belongs to one session and one immutable input, including any per-turn
  options. Reusing it with different content fails. Reusing it with the same
  content retrieves the recorded outcome or reconciles the existing request;
  it never dispatches a second request merely because the caller retried.
* Persist a prepared record containing the ID and complete input before external
  work. Persist a running record before dispatch, then attach provider request
  IDs as soon as available. A crash between the running record and dispatch is
  conservatively uncertain.
* Commit the response, native conversation update, usage, and terminal status
  together before returning. A durable journal commit record distinguishes a
  committed turn from partially written data. Derived indexes can be rebuilt;
  a partially written response must never look complete.

Turn states are prepared, running, completed, failed, cancelled, uncertain,
and abandoned. Completed means a complete provider response is durably available;
its finish reason is recorded separately. Failed and cancelled are terminal only
when the request's outcome is known. Partial output may still exist. Uncertain
means dispatch or completion cannot yet be established. It blocks new inputs to
that session until reconciled or explicitly abandoned. Prepared and running
turns also prevent another turn from advancing the session concurrently.

On reopening, acquire exclusive session ownership and reconcile unfinished work:

1. Return committed outcomes without contacting the model again.
2. Dispatch a prepared turn only if its journal proves dispatch never began.
3. For a running turn, retrieve the provider result or reconnect to a surviving
   request handler when supported. Continue the same request only when the
   adapter can do so without duplicating inference. Before starting a replacement
   handler, ensure the previous handler cannot still commit to the session.
4. If the adapter cannot establish the outcome or safely continue the request,
   persist uncertain and return a structured recovery-required error with the
   turn ID, known partial output, and available recovery actions. Do not silently
   retry. Later recovery attempts may reconcile the same uncertain request.

Normal recovery is handled by the interface. The caller only needs a stable
turn ID and to reopen the session. For irrecoverable uncertainty, provide an
explicit abandon operation. Preserve the audit trail and acknowledge that remote
inference or billing may remain unknown. Abandoned is a terminal local decision;
late results remain audit records and cannot silently advance the conversation.

Current adapters send stateless requests and replay committed native history.
OpenAI requests use store=False. A durably recorded terminal receipt can be
reconciled locally after a crash before the conversation commit. When a remote
response was lost, these transports cannot retrieve it and expose uncertainty.
No automatic resend or remote process reattachment is implied. After close,
old handlers are fenced from all writes, including late audit writes.

After abandonment, continue from the last committed conversation only if the
adapter can exclude the abandoned request from future context. If provider-held
state cannot be reconciled, require an explicit reset or a new session. Any
fresh attempt uses a new turn ID and records its relation to the abandoned turn.
Do not invent missing assistant responses or include partial output as a complete
conversation turn.

Cancellation is an out-of-band operation so it can interrupt a blocking input.
Request provider cancellation when supported and commit the observed outcome.
A completion already committed wins a race with cancellation. Closing a local
connection does not prove remote cancellation; an unconfirmed outcome remains
uncertain. Timeouts follow the same rule.

close releases local connections and session ownership while retaining durable
session data. With an active turn, it first follows the cancellation path and
records any uncertainty. A disconnected caller is not itself evidence that
remote inference stopped. Cancellation and close must not allow stale request
handlers to append conversation state after session ownership has changed.

Automatic retries are limited to failures known not to have executed, or to a
provider's documented recoverable/idempotent operation. Keep individual attempts
and their usage in the journal. Exactly-once provider billing cannot be promised
without corresponding provider support.

6. Verification and remaining decisions
---------------------------------------

Keep tests in experimental/test_llm.py. Cover behavior rather than only the
shape of the implementation:

* Initialization rejects unsupported model/mode/auth/effort combinations.
* Single-turn context is fresh; multi-turn native state survives reopening.
* OAuth refresh and API-key resolution work without leaking credentials into
  session records, silently switching auth methods, or duplicating requests.
* Completed responses are recoverable and repeated prompts remain distinct.
* Turn-ID collisions fail; crash injection around prepare, dispatch, and commit
  neither loses committed results nor silently repeats uncertain inference.
* Cancellation races, timeouts, and unavailable provider recovery produce the
  documented terminal or recovery-required outcomes.
* Abandoned requests and late results cannot silently alter conversation state.
* Conflicting resumes and simultaneous session writers fail safely; recognized
  interrupted initialization can be recovered without overwriting unrelated data.
* Missing usage remains unknown; finish reasons and attempt usage are preserved.
* Context limits fail explicitly and any reset is journaled.

Most tests should use fake provider responses. Separate opt-in integration tests
exercise real provider requests and authentication. The standard suite requires
neither live credentials nor paid model calls.

Run the standard suite from the repository root:

    .venv/bin/python -m unittest experimental.test_llm

For a deliberate live test, set EXPERIMENTAL_LLM_LIVE=1, select
EXPERIMENTAL_LLM_MODEL and EXPERIMENTAL_LLM_AUTH, and supply the matching
credentials. The live test checks two turns and reopening. It makes model calls.

Keep the capability registry and provider adapters explicit as coverage expands.
Verify live authentication, model availability, and native replay for each account
and endpoint; do not infer those properties from mock transport tests alone.

Reference implementation to consult: gobench/llm_conversation.py and the direct
model-request paths in arena.py. Keep the new interface independent of arena.py.
